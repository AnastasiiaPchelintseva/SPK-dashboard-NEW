# Платформа вайбкод-проектов

Общие правила для всех проектов этого репозитория: стек, конфигурация, база данных, вход,
пользователи, сессии и панель администратора. Каждый проект реализует авторизацию **сам**,
по этому шаблону. Общего сервиса входа нет: у каждого проекта свои пользователи, сессии и
роли в своей базе.

Новый проект строится по этому документу с первого коммита. Существующие проекты переводятся
на него по одному, см. «Переход проектов».

Источник документа — `PLATFORM.md` в корне общего репозитория `vibecodeprojects`. В корне
каждого проекта лежит его копия: она уходит в личный репозиторий проекта вместе с остальным кодом.

## 1. Стек

Проект пишется на **Python** или на **.NET**.

| | .NET | Python |
|---|---|---|
| Веб | ASP.NET Core MVC (Razor) | FastAPI + Jinja2 |
| БД | EF Core + Npgsql, миграции EF | SQLAlchemy + Alembic |
| Вход через Яндекс | OAuth-обработчик ASP.NET Core | Authlib |
| Образец | KbService (`Security/YandexAuth.cs`) | будет сделан при переходе первого Python-проекта |

Streamlit как веб-интерфейс по шаблону не подходит: в нём нет управляемых cookie, форм с защитой
от подделки запросов и своих маршрутов для входа.

## 2. Конфигурация

**Правило 1: приложение обязано запускаться без параметров вовсе** — с пустым `.env` и пустой
таблицей настроек. Оно не падает и не уходит в перезапуск по кругу ни при каком отсутствующем
или неверном параметре.

**Правило 2: все параметры, нужные для работы системы, задаются в панели администратора.**
Если какой-то функции не хватает настроек, она выключена, а в панели администратора видно,
что именно нужно заполнить.

В `.env` приложения остаются только:

| Переменная | Что | Если не задана |
|---|---|---|
| `ADMIN_PASSWORD` | пароль локального пользователя `admin` | вход администратора выключен, в логе предупреждение |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | подключение к PostgreSQL | по умолчанию `localhost`, `5432`, имя проекта, пустой пароль; при неудаче — страница «Не настроено» |
| `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` | приложение на oauth.yandex.ru | вход через Яндекс выключен, работает только `admin` |

Имена переменных одинаковые во всех проектах.

**Без базы данных.** Если подключиться к PostgreSQL не удалось (параметров нет или они
неверные), приложение работает в режиме «Не настроено»:
- на любой запрос отдаёт страницу «Не настроено»: каких параметров не хватает и почему не
  удалось подключиться, например «нет пароля», «база недоступна», «неверный пароль».
  Значения параметров на странице и в логе не показываются;
- повторяет подключение в фоне, например раз в 30 секунд. После удачного подключения
  применяет миграции и начинает работать без перезапуска;
- остальные функции, включая вход, в этом режиме недоступны.

**При выкладке всё обязательно.** Правило 1 — про устойчивость приложения, а не разрешение
выкладывать его недонастроенным. `ops/deploy.sh` не выкладывает проект, пока в
`.secrets/<проект>.env` не заполнены все переменные из таблицы выше, включая `ADMIN_PASSWORD`.

Всё остальное хранится в таблице настроек в БД и меняется в панели администратора:
разрешённые домены, интеграции (почта, LLM, внешние API),
режимы работы и т. п. В коде у каждой настройки есть значение по умолчанию. Изменения
применяются без перезапуска и пишутся в журнал аудита.

- Секреты (пароли, токены интеграций) после сохранения в панели не показываются, только маска
  и кнопка «заменить». В журнал аудита и логи их значения не попадают.
- Параметры развёртывания — порты, привязка к интерфейсу, тег образа, каталоги на хосте —
  относятся к `docker compose`, а не к приложению. Они лежат в `.secrets/<проект>.env`
  рядом с переменными выше, но приложение их не читает (см. `DEPLOY.md` общего репозитория).

## 3. База данных

- PostgreSQL. У каждого проекта **своя база и свой пользователь БД** с правами только на неё.
- Схема меняется только миграциями. Миграции применяются **при старте** приложения.
- Ключи шифрования cookie (.NET Data Protection) хранятся в этой же базе. Перезапуск
  и новая выкладка не разлогинивают пользователей.

## 4. Пользователи

### Кто такой пользователь

- Пользователь определяется по **Яндекс `id`** (поле `id` из `login.yandex.ru/info`). Он
  запоминается при первом входе и дальше ищется только по нему.
- Домены `pik.ru`, `pik-industry.ru`, `prefabtech.ru`, `pik-element.ru` — **алиасы одной
  организации** в Яндекс 360. `ivanov@pik.ru` и `ivanov@prefabtech.ru` — один и тот же человек.
- **Имя пользователя** (`username`) — часть email до `@` в нижнем регистре:
  `Ivanov@pik-industry.ru` → `ivanov`. Имя уникально в пределах проекта.
- Имя `admin` **зарезервировано** за локальным администратором. Пользователь Яндекса с таким
  именем не входит: он видит сообщение «обратитесь к администратору», в журнал пишется отказ.
- При каждом входе email, имя пользователя и отображаемое имя **обновляются** из данных Яндекса.
- Локальных паролей у пользователей нет. Исключение — `admin`, см. «Локальный администратор».

### Регистрация

- Любой, кто прошёл вход через Яндекс с адресом на разрешённом домене, **регистрируется
  автоматически**. Что ему доступно, определяют роли проекта (см. «Роли»).
- Список разрешённых доменов — настройка в панели администратора. По умолчанию это четыре
  домена выше. Сравнивается домен `default_email` целиком, поддомены не проходят.
- Администратор может **заранее создать пользователя**, указав только email. Имя берётся
  из email так же, без домена. При первом входе через Яндекс такая запись находится по имени
  пользователя среди записей без Яндекс `id`, и к ней привязывается `id`. Так заранее выданные
  роли сохраняются.
- Если имя пользователя уже занято записью с **другим** Яндекс `id` (например, у нового сотрудника
  тот же адрес, что был у уволенного), вход отклоняется с сообщением «обратитесь к
  администратору», в журнал пишется конфликт. Администратор переименовывает или удаляет
  старую запись.

### Состояния

| Состояние | Когда | Вход |
|---|---|---|
| Создан | администратор завёл пользователя, тот ещё не входил | разрешён, после входа — «Активен» |
| Активен | пользователь входил хотя бы раз | разрешён |
| Заблокирован | администратор заблокировал | запрещён, все сессии удалены |

- **Блокировка** сразу удаляет все сессии пользователя: следующий его запрос уже не пройдёт.
  Заблокированный при попытке войти видит «Доступ заблокирован», а не ошибку.
- Уволенный сотрудник теряет почту на доменах организации и не может войти через Яндекс.
  Действующие сессии у него закончатся сами через 7 дней без активности. Сразу отключить
  его может только администратор — блокировкой.
- Администратор может поменять пользователю email. После привязки к Яндексу email
  перезаписывается при каждом входе, поэтому правка нужна в основном для заранее созданных.

## 5. Вход

### Через Яндекс

- OAuth 2.0 Authorization Code + PKCE, `https://oauth.yandex.ru/authorize`, scopes
  `login:email` и `login:info`. Callback — `/signin-yandex`.
- Яндекс **всегда спрашивает, каким аккаунтом войти**: в запрос авторизации добавляется
  `force_confirm=yes`. Иначе браузер молча входит под последним аккаунтом Яндекса, и сменить
  пользователя, например личный аккаунт на рабочий, нельзя.

  ```csharp
  // .NET: в настройке OAuth-обработчика (AddOAuth)
  options.AdditionalAuthorizationParameters["force_confirm"] = "yes";
  ```

  ```python
  # Python (Authlib)
  return await oauth.yandex.authorize_redirect(request, redirect_uri, force_confirm="yes")
  ```
- На oauth.yandex.ru у каждого проекта **своё приложение**: Redirect URI
  `https://<домен проекта>/signin-yandex`, доступы «Адрес электронной почты» и
  «Логин, имя и фамилия».
- После ответа Яндекса: проверить домен → найти пользователя (по `id`, затем среди заранее
  созданных) → проверить состояние → обновить поля → создать сессию → записать в журнал.

### Локальный администратор

- Всегда есть пользователь `admin` с ролью `administrator`. Он создаётся при старте, если его нет.
- Пароль задаётся в `ADMIN_PASSWORD`. В базе хранится только хэш (.NET `PasswordHasher`,
  Python `argon2` или `bcrypt`). При старте хэш сверяется с `.env`. Если пароль изменился,
  хэш обновляется, а все сессии `admin` удаляются.
- Вход — отдельная форма, ссылка «Вход администратора» на странице входа. Не больше 5 неудачных
  попыток за 15 минут с одного IP, дальше пауза. Неудачные попытки пишутся в журнал.
- `admin` нельзя заблокировать, удалить, понизить в роли или привязать к Яндексу.

### Вход для разработки

По желанию проекта в режиме разработки (Development) можно оставить упрощённый вход без Яндекса.
В остальных окружениях его быть не должно.

## 6. Сессии и cookie

- Сессии хранятся **на сервере**, в таблице БД. В cookie лежит только случайный идентификатор
  сессии. В .NET это `ITicketStore`, в Python — свой токен (32 случайных байта). В базе хранится
  хэш идентификатора, а не он сам.
- Сессия живёт **7 дней с последней активности**. Если 7 дней запросов не было, сессия удаляется,
  и пользователь входит заново. Время активности обновляется не чаще раза в минуту.
- В сессии хранятся: пользователь, время создания, время последней активности, IP (из
  `X-Forwarded-For` от nginx), User-Agent.
- Каждый пользователь видит **свои** сессии и может завершить любую из них. Администратор видит
  и завершает сессии всех пользователей. «Выйти» удаляет текущую сессию на сервере.
- Параметры cookie: `HttpOnly`, `SameSite=Lax`, `Secure` по схеме запроса (`SameAsRequest`),
  скользящий срок (`SlidingExpiration`) 7 дней. Имя cookie своё у каждого проекта.
- POST-формы защищены от подделки запросов (antiforgery-токен).

## 7. Роли

- Роли у каждого проекта свои.
- Роль `administrator` есть во всех проектах и даёт **полный доступ** к проекту.
- Новый пользователь **не имеет роли**. Что может пользователь без роли, проект определяет сам:
  например, только видит экран «Доступ не выдан, обратитесь к администратору» или читает
  общедоступные разделы. Это описывается в `AGENTS.md` проекта.
- Роль выдаёт администратор в панели администратора.

## 8. Панель администратора

Доступна только роли `administrator`. Обязательные разделы:

- **Пользователи:** список с поиском и фильтром по состоянию; создание по email; смена email
  и роли; блокировка и разблокировка.
- **Сессии:** все активные сессии (пользователь, IP, User-Agent, создана, последняя активность)
  с удалением по одной и всех сессий пользователя.
- **Настройки:** все параметры приложения (см. «Конфигурация»).
- **Журнал аудита.**

## 9. Журнал аудита

Пишется в БД. В каждой записи: время, кто (пользователь или `admin`), IP, действие, над кем
или чем, старое и новое значение. Обязательные события:

- вход через Яндекс; отказ (домен, блокировка, имя `admin`, конфликт имени);
- вход `admin`, неудачная попытка, пауза после неудачных попыток;
- выход; удаление сессии; истечение сессии необязательно;
- создание пользователя, смена email, роли, состояния;
- изменение настроек (без значений секретов).

## 10. Таблицы

Минимальный набор, имена полей — ориентир:

```
users           id, yandex_id (уникальный, пусто до первого входа), username (уникальный),
                email, display_name, role (пусто — без роли), status (created | active | blocked),
                is_local_admin, password_hash (только у admin), created_at, last_login_at
sessions        id, user_id, token_hash, created_at, last_activity_at, ip, user_agent
audit_log       id, at, actor_user_id, ip, action, target, old_value, new_value
settings        key, value, is_secret, updated_at, updated_by
data_protection_keys   только .NET: ключи шифрования cookie
```

## 11. Переход проектов

Проекты переводятся по одному. Порядок для каждого: сверка с разделами этого документа →
план → миграция данных пользователей → выкладка.

Насколько проект соответствует шаблону и что осталось сделать, ведётся в общем репозитории
`vibecodeprojects`, отдельным файлом на каждый проект: `platform-status/<проект>.md`. Копия
кладётся в корень проекта как `PLATFORM-STATUS.md` и уходит в личный репозиторий: по ней
владелец проекта сверяет соответствие и видит замечания. Копию не правят; исправленное замечание
или вопрос по нему — сообщить тому, кто ведёт общий репозиторий.

## 12. Структура проекта и публикация

Проект публикуется на сервер команды из общего репозитория (`ops/deploy.sh`, см. `DEPLOY.md` там).
Чтобы это работало без доработок, в корне проекта лежат:

| Файл | Что |
|---|---|
| `AGENTS.md` | описание, структура, команды, что может пользователь без роли; ссылка на `PLATFORM.md` |
| `PLATFORM.md` | копия этого документа, её не править |
| `PLATFORM-STATUS.md` | копия сверки проекта с этим документом и замечаний (раздел 11), её не править |
| `docker-compose.server.yml` | как проект запускается на сервере |
| `.env.example` | переменные раздела 2 без значений |

**`docker-compose.server.yml`:**

- образ собирается из исходников: `build:` и `image: ${<ПРОЕКТ>_IMAGE:-<проект>:local}` — тег
  образа подставляет скрипт выкладки;
- в контейнер передаются только переменные раздела 2 (`ADMIN_PASSWORD`, `DB_*`, `YANDEX_*`);
  параметры развёртывания (порт, привязка, каталоги на хосте) используются только в самом compose;
- PostgreSQL — серверная, на хосте, не в контейнере: `DB_HOST` по умолчанию `host.docker.internal` и
  ```yaml
  extra_hosts:
    - "host.docker.internal:host-gateway"
  ```
- порт для внешнего nginx: `"${APP_BIND:-127.0.0.1}:${APP_PORT:-<порт>}:<порт в контейнере>"`;
  номер порта на сервере выдаётся в общем репозитории;
- `restart: unless-stopped`; данные, которые не в базе, — в именованных томах;
- без своих nginx, PostgreSQL и сертификатов: HTTPS и адрес даёт внешний nginx.

**Приложение за внешним nginx:**

- адрес — `https://<проект>.userapp.dsk2.picompany.ru`, приложение работает **в корне** адреса, не
  под путём;
- доверяет заголовкам `X-Forwarded-For` (IP в журнале и сессиях) и `X-Forwarded-Proto` (схема для
  cookie `Secure` и адреса возврата из Яндекса); своего редиректа на HTTPS нет;
- логи — в stdout;
- желательно — адрес проверки готовности, который отвечает 200, когда база подключена (например,
  `/health/ready`).

**Репозиторий:** секретов и `.env` в git нет, только `.env.example` без значений.

## 13. Новый проект: чеклист

1. Стек — Python или .NET (раздел 1).
2. Своя база и свой пользователь PostgreSQL, миграции при старте.
3. Таблицы из раздела 10, вход через Яндекс и локальный `admin`, серверные сессии.
4. Панель администратора: пользователи, сессии, настройки, журнал.
5. В `.env` — только переменные из раздела 2. Проверка: запуск с пустым `.env` → страница
   «Не настроено», а не падение; с БД, но без ключей Яндекса → работает вход `admin`.
6. Приложение на oauth.yandex.ru с Redirect URI `https://<домен>/signin-yandex`.
7. `AGENTS.md` проекта ссылается на копию `PLATFORM.md` в корне проекта и описывает, что может
   пользователь без роли.
8. В общем репозитории: заведён `platform-status/<проект>.md`, копии `PLATFORM.md` и
   `PLATFORM-STATUS.md` разложены командой `ops/sync-platform.sh`.
9. Структура и публикация — раздел 12: `docker-compose.server.yml`, работа за внешним nginx.
